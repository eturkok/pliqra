# 2.4.0 — observe the behavior behind an unchanged endpoint

Pliqra 2.4.0 is the stable community gateway release for the [documented support envelope](../SUPPORT.md).

## Scheduled model behavior checks

Configure opt-in schedules in **Model health** or the administrator API. Exercise chat responses/custom expected text, complete Chat Completions streams, a small JSON Schema response and requested tool arguments, with optional full-response latency limits. Each schedule targets one deployment directly, with no cache or fallback.

The overview and dashboard retain per-check last test, last success, most recent outcome change and cycle history. Failure and recovery transitions create notifications; repeating the same failure does not repeat the notification. Execution errors, assertion failures, interruptions and configuration changes remain distinct.

Daily UTC cycle reservations, per-call output-token/timeout bounds, project budget accounting and workspace concurrency constrain real model calls. Shared PostgreSQL serializes claims across replicas. Site placement, maintenance, draining and fencing apply. Started work is not replayed; a later regular cycle can run when due. Pausing stops subsequent checks after a started call finishes.

Observations do not change declared/verified capabilities, circuit health, application contracts or traffic policy. Configuration is encrypted at rest; this flow retains no response text. These tests detect violations of selected expectations, not model identity or arbitrary semantic drift.

[Configuration, APIs, limits and real-model evidence](../BEHAVIOR_CHECKS.md). Actual SmolLM2 chat/streaming checks and a custom text expectation were exercised before release. Controlled regression/recovery is a separate synthetic test.

## Upgrade and recovery

**Database schema 6 → 7.** Back up the database and encryption key, stop every old writer, and upgrade shared sites together. Unchanged bindings remain valid: inference contract 5 and Protocol 1.0 are unchanged.

Schema-6 SQLite and PostgreSQL portable archives can restore into 7. Restored behavior schedules are paused until an administrator reviews them. Current-schema history and last success survive restart and restore; restore does not replay started checks. Returning to 2.3 requires its matching pre-upgrade schema-6 backup in separate storage.

## Distribution and acceptance

- Native Linux AMD64/ARM64 image; non-root execution, Apache-2.0 files, per-platform SBOM/provenance and anonymous digest verification.
- Python 3.13/3.14, real PostgreSQL, JavaScript/Go clients, legacy/current compatibility and an unsuppressed dependency scan.
- Exact-image acceptance exercises scheduled execution, a controlled same-endpoint tool regression, retained last success, deduplicated notifications, recovery, daily limits and restart persistence, alongside routing, quotas, fleet and streaming.
- The committed 30-minute synthetic soak, installed/official clients, 2.3.0 image upgrade, schema-6 restore and isolated rollback gate publication. Attached reports contain the actual measurements.

SDK **1.0.1** is reused byte for byte from its original release. Protocol **1.0**, legacy **0.1** compatibility and inference contract **5** remain unchanged. Helm **0.3.1** has an independent lifecycle; explicitly select the 2.4.0 image digest and validate the override in your cluster.

Synthetic CI and local real-model evidence describe their tested workload. Production capacity, geographic failover, vendor safety and recovery objectives remain installation-specific.

## Verified delivery — 11 November 2026

The exact published AMD64/ARM64 image passed native smoke tests and anonymous digest verification. The 30-minute synthetic soak completed **9,000 requests**, all HTTP 200, in **1,800.12 seconds**. Observed end-to-end p95 was **421.35 ms**; west-gateway RSS changed by **+4,176 KiB**. A separate bounded load sample completed **1,800 calls**, all HTTP 200. These are CI workload measurements, not production sizing.

The same image completed five behavior cycles, including one automatic cycle: passed → passed → failed → failed → passed at an unchanged endpoint fingerprint. The tool failure retained last success; the repeated failure produced no duplicate transition notification. Recovery, the daily cap and restart persistence passed without changing declared or verified capabilities.

Upgrade from 2.3.0 retained bindings, encrypted credentials, keys, events and quota usage. Schema-7 monitoring history survived restart and restored paused, with no replay. Schema-6 restore, session revocation and isolated rollback to 2.3.0 also passed. SDK 1.0.1 assets match the previously verified release byte for byte.
